`v0.3.0-rc.1` is the first public AVP release candidate. It is a published prerelease, not a stable conformance target and not a `1.0` stability claim.

## Protocol and conformance scope

Alpha 2 consolidates the AVP v0.1 protocol/conformance surface around ten profiles:

- Core episode lifecycle and result separation;
- Evidence / Artifact identity and integrity;
- Oracle evaluation and execution-failure separation;
- Security capability, secret, credential-context, and assurance boundaries;
- ScenarioTemplate / ScenarioInstance deterministic materialization and identity;
- Environment lifecycle, observation, snapshot/restore, time, fault, projection, and semantic diff;
- MCP tool interoperability verification without replacing MCP protocol authority;
- OpenTelemetry correlation/mapping without making telemetry an Oracle;
- Subject Adapter interoperability without standardizing one transport;
- Artifact Trust / attestation authentication and evaluator-owned trust-policy acceptance.

The release contains 87 indexed normative requirements, 71 registered language-neutral TCK cases, and 10 conformance profiles at the Alpha 2 acceptance baseline.

## Compatibility

This is the first public AVP release candidate. There is no earlier published AVP compatibility target against which a migration guide can be written.

Pre-1.0 protocol evolution remains experimental. A future `0.y.z` release may include explicitly documented breaking normative changes according to `docs/RELEASE_PROCESS.md`.

## Security and trust notes

The release candidate preserves these boundaries:

- Subject-visible capabilities and evaluator-private authority remain separated and fail closed.
- API capability mediation does not imply operating-system, process, network, tenant, container, VM, or sandbox isolation.
- Hidden evaluator material, credentials, Oracle material, and future fault schedules are not made Subject-visible by conformance requirements.
- OpenTelemetry data is observational and non-authoritative; it cannot become a second Oracle or a mandatory carrier of protected raw payloads.
- Evidence exact-byte integrity is distinct from attestation authentication and trust-policy acceptance.
- Attestation signer hints and unauthenticated observations do not become authoritative signer identity.
- Production signing, key management, PKI, transparency, revocation/timestamp services, and equivalent deployment trust infrastructure remain outside AVP Core ownership.

The cross-profile security review is recorded in `docs/acceptance/alpha2-security-composition-review.md`.

## Reference implementation

The `avp-reference` package remains a non-normative reference implementation. It provides executable evidence for the current contracts, including Scenario compilation, Environment behavior, MCP verification, OpenTelemetry mapping, Subject Adapter execution, Artifact/Evidence handling, Oracle execution, and Artifact Trust verification.

The RC package version uses PEP 440 form `0.3.0rc1`; the immutable repository tag is `v0.3.0-rc.1` and resolves directly to `ef199124017b0dcc8c4a966d00c4f407760f9a06`.

Pre-publication CI validated the built wheel in two independent clean environments. Post-publication acceptance goes further: it downloads the assets from the public GitHub Release, verifies the release/tag/source binding and SHA-256 evidence, installs the published wheel without repository constraints in a clean base consumer environment, and installs the same published wheel with the non-normative `[conformance]` extra in a separate environment to run every registered TCK profile. The extra supplies reference-validation dependencies such as OpenTelemetry without promoting them into mandatory package dependencies or AVP protocol requirements.

## Known non-goals

This release candidate does not claim:

- production-grade signed/attested Artifact publication;
- a required signing algorithm, PKI, key manager, transparency service, or deployment isolation technology;
- PostgreSQL/MySQL state adapters, browser execution, network fault proxying, virtual-clock services, container runtime, or microVM execution from Alpha 3;
- stability equivalent to a final 1.0 protocol.

## AEP lifecycle

AEP-0001 through AEP-0008 remain `Accepted` protocol directions. The RC publication does not automatically transition them to `Final`.

Any AEP `Final` transition remains a separate governed maintainer decision based on the project's lifecycle rules; it is not inferred from reference implementation success or prerelease publication.

## Publication boundary

The tag and GitHub Prerelease have been published and independently validated. No PyPI or other package-index publication is implied or authorized by this release. Stable `v0.3.0`, any AEP `Final` transition, and Alpha 3 implementation work remain separate governance boundaries.
